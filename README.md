# Python Port Scanner

`socket` 표준 라이브러리만으로 만든 간단한 TCP connect 포트 스캐너입니다. (nmap `-sT` 스캔의 간이 버전)

> ⚠️ 본인 소유 또는 스캔이 허가된 호스트(127.0.0.1, scanme.nmap.org 등)에만 사용하세요.

## 실행 방법

```bash
# 인자 없이 실행하면 호스트와 포트 범위를 직접 입력받음 (Level 1)
python3 scanner.py

# CLI 인자로 실행 (Level 2)
python3 scanner.py --host 127.0.0.1 --ports 1-1000

# 순차 스캔 (스레드 1개)
python3 scanner.py --host 127.0.0.1 --ports 1-1000 --threads 1

# 스레드 수, 타임아웃 지정
python3 scanner.py --host scanme.nmap.org --ports 20-100 --threads 100 --timeout 0.5
```

| 옵션 | 설명 | 기본값 |
|---|---|---|
| `--host` | 대상 IP 또는 도메인 | (입력받음) |
| `--ports` | 포트 하나(`80`) 또는 범위(`1-1000`) | (입력받음) |
| `--threads` | 동시 스레드 수, `1`이면 순차 스캔 | 50 |
| `--timeout` | 포트당 연결 타임아웃(초) | 1.0 |

### 실행 결과

테스트용으로 22, 80, 3306번 포트에 리스너를 띄운 뒤 스캔했습니다. (135, 445는 Windows 기본 서비스)

```
$ python scanner.py --host 127.0.0.1 --ports 1-1000 --timeout 0.5
Scanning 127.0.0.1 (127.0.0.1) ports 1-1000 with 50 threads...
Port 22 (ssh): OPEN
Port 80 (http): OPEN
Port 135 (epmap): OPEN
Port 445 (microsoft-ds): OPEN
Scan finished in 10.29s (open: 4, closed: 996)
```

## 구현 과정

### 1. 포트 하나 검사하기 — `scan_port()`
TCP 소켓을 만들고 `connect_ex((host, port))`로 연결을 시도합니다. 반환값이 `0`이면 연결 성공(OPEN), 그 외의 에러 코드(연결 거부, 타임아웃 등)는 CLOSED로 판단합니다.
`settimeout()`을 설정하지 않으면 응답이 없는 포트(방화벽이 패킷을 버리는 경우)에서 OS 기본 타임아웃(수십 초)까지 기다리게 되므로 반드시 설정했습니다.
`with` 문으로 소켓을 열어 검사가 끝나면 바로 닫히도록 했습니다. 소켓을 닫지 않으면 포트 수천 개를 스캔할 때 파일 디스크립터가 고갈됩니다.

### 2. 입력 처리 — `parse_ports()`, `argparse`
`"80"` 같은 단일 포트와 `"1-1000"` 같은 범위를 모두 `range`로 바꾸고, 1~65535 범위를 벗어나면 에러를 냅니다.
`argparse`로 `--host`, `--ports`, `--threads`, `--timeout`을 받습니다. 인자를 주지 않으면 `input()`으로 직접 입력받도록 해서 Level 1 요구사항도 만족시켰습니다.
도메인을 입력하면 `socket.gethostbyname()`으로 IP로 변환합니다. (DNS 조회를 포트마다 반복하지 않도록 한 번만 수행)

### 3. 멀티스레딩 — `ThreadPoolExecutor`
포트 스캔은 CPU가 아니라 네트워크 응답을 기다리는 시간이 대부분인 I/O 작업이라, 파이썬 GIL이 있어도 스레드로 큰 속도 향상을 얻을 수 있습니다.
`ThreadPoolExecutor(max_workers=N)`와 `pool.map()`을 사용해 N개의 포트를 동시에 검사합니다. `map()`은 입력 순서대로 결과를 돌려주므로 출력이 포트 번호순으로 정렬됩니다.

### 4. 서비스 이름 매핑 — `service_name()`
`socket.getservbyport(port, "tcp")`로 OS의 서비스 목록(`/etc/services`, Windows는 `C:\Windows\System32\drivers\etc\services`)을 조회합니다. 목록에 없는 포트는 직접 만든 `COMMON_SERVICES` 딕셔너리에서 찾고, 그래도 없으면 `unknown`을 출력합니다.

### 5. 시간 측정 — 순차 vs 스레드
`time.time()`으로 스캔 전후 시간을 재서 비교했습니다. (127.0.0.1, 포트 1-1000, 타임아웃 0.5초, Windows 11)

| 방식 | 소요 시간 |
|---|---|
| 순차 (`--threads 1`) | 503.86s |
| 스레드 50개 | 10.29s |

**약 49배 빨라졌습니다.** 스레드 수(50)와 거의 같은 비율로, 대기 시간이 대부분인 I/O 작업이라 병렬화 효과가 그대로 나타났습니다.

참고: Windows에서는 닫힌 포트에 연결하면 RST를 받아도 SYN을 몇 번 재전송한 뒤 약 2초 후에야 실패를 반환합니다. 그래서 닫힌 포트마다 타임아웃(0.5초)을 꽉 채워 기다리게 되어, 1000 ÷ 50 × 0.5초 ≈ 10초가 걸렸습니다. Linux에서는 RST를 받는 즉시 실패를 반환하므로 같은 스캔이 1초 이내로 끝납니다.

## 체크포인트 질문 답변

### Q1. 포트 하나를 확인할 때 3-Way Handshake의 어느 단계까지 일어나는가?
**3단계 전부 일어납니다.** `connect_ex()`는 OS의 일반 TCP 연결 기능을 그대로 사용하기 때문입니다.

- **열린 포트:** `SYN →` / `← SYN-ACK` / `ACK →` 로 핸드셰이크가 완료되어 연결이 실제로 맺어지고, 곧바로 소켓을 닫으면서 `FIN`(또는 `RST`)이 전송됩니다.
- **닫힌 포트:** `SYN →` / `← RST-ACK` 로 1단계에서 거부됩니다.
- **필터링된 포트(방화벽):** `SYN →` 이후 응답이 없어 타임아웃이 발생합니다.

이것이 nmap의 **TCP Connect 스캔(`-sT`)** 방식입니다. 연결이 완전히 맺어지므로 대상 서버의 로그에 기록이 남습니다. 반면 nmap의 기본 방식인 **SYN 스캔(`-sS`, half-open)** 은 SYN-ACK를 받으면 ACK 대신 RST를 보내 핸드셰이크를 2단계에서 끊습니다. 대신 raw 소켓으로 패킷을 직접 만들어야 해서 관리자 권한이 필요합니다.

### Q2. `connect`와 `connect_ex`의 차이, 스캐너에 `connect_ex`가 더 적합한 이유
- `connect()`: 연결에 실패하면 `ConnectionRefusedError`, `TimeoutError` 같은 **예외를 발생**시킵니다.
- `connect_ex()`: 예외 대신 **에러 코드(정수)를 반환**합니다. 성공하면 `0`, 실패하면 `errno` 값(Linux의 연결 거부는 `111`, Windows는 `10061`)을 돌려줍니다.

포트 스캐너에서는 대부분의 포트가 닫혀 있으므로 "실패"가 예외 상황이 아니라 정상적인 결과입니다. `connect()`를 쓰면 매번 `try/except`로 감싸야 하고 코드가 지저분해집니다. `connect_ex()`는 `== 0` 비교 하나로 OPEN/CLOSED를 판별할 수 있어 더 간결하고, 반환된 에러 코드로 거부(closed)인지 타임아웃(filtered)인지 구분할 수도 있습니다.

### Q3. 스레드를 너무 많이 띄우면(예: 1000개) 생기는 문제
1. **파일 디스크립터 고갈:** 소켓 하나가 파일 디스크립터 하나를 차지합니다. Linux의 기본 제한(`ulimit -n`)은 보통 1024라서, 1000개를 동시에 열면 `OSError: [Errno 24] Too many open files`가 발생할 수 있습니다. 이 에러를 CLOSED로 잘못 판정하면 결과가 틀어집니다.
2. **대상 서버의 방어 로직:** 짧은 시간에 연결 요청이 몰리면 IDS/IPS나 방화벽이 포트 스캔 또는 SYN flood 공격으로 탐지해 IP를 차단합니다. 그러면 이후 포트가 모두 타임아웃되어 열린 포트도 닫힌 것처럼 보입니다. 서버 입장에서는 실제로 DoS가 될 수도 있습니다.
3. **로컬 자원 낭비와 네트워크 혼잡:** 스레드마다 메모리(스택)를 차지하고 컨텍스트 스위칭 비용이 늘어납니다. 또 패킷이 한꺼번에 몰려 손실되면 열린 포트를 놓칠 수 있어 정확도가 떨어집니다.
4. **수확 체감:** 스레드를 일정 수 이상 늘리면 네트워크 대역폭이나 대상 서버의 처리 속도가 병목이 되어 더 이상 빨라지지 않습니다.

그래서 50~100개 정도의 적당한 스레드 풀을 사용하는 것이 좋습니다. nmap도 `-T0`~`-T5` 타이밍 옵션으로 동시 요청 수와 속도를 조절합니다.
